# 2026-11-28 — OLED 전송량 비교 시뮬레이션 결과

## 목적

실물 S32K144EVB가 없는 상황에서 최적화 브랜치의 **실제 `src/oled.c`** 를 리눅스 GCC에서 컴파일하고, SSD1306 128x64의 GDDRAM(1,024B) 모형에 명령과 데이터를 적용하여 프레임별 화면 무손실 정합과 버스 전송량을 측정한다.

이 결과는 MCU CPU Cycle, eDMA 동작 시간, 전력, 실물 I2C 파형을 측정한 것이 **아니다**.

## 재현

```bash
bash tests/run_oled_traffic_sim.sh
```

GitHub Actions의 `.github/workflows/host-tests.yml`에서도 자동 실행한다.

- 사용하는 실제 소스: `src/oled.c`, `src/oled_font5x7.c`.
- 모의 장치: `tests/test_oled_traffic_sim.c`. `0x21` 열 주소와 `0x22` Page 주소를 해석하여 후속 데이터 트랜잭션을 가상 GDDRAM에 쓴다.
- 모든 갱신 후 `memcmp(OLED_GetBuffer(), panel, 1024)==0`를 검사한다.
- 모의 장치가 버스 전송 완료를 즉시 통지하므로 지연/CPU 시간 결과로 사용할 수 없다.
- 최적화 모드 버스 바이트 = 모든 전송의 `데이터 길이 + I2C 7비트 주소 바이트 1 + SSD1306 control 바이트 1`의 합.
- 비교 대상 기존 브랜치 `final/radar-system-20261126`는 매번 6개 단일바이트 명령 트랜잭션 + 8개 128바이트 데이터 트랜잭션을 실행한다. 따라서 `6×3 + 8×(128+2) = 1,058` 버스 바이트/프레임.
- 통신 시작/정지 간 휴지, 실제 ACK/NACK, Clock stretching, 버스 Rise time, GPIO/IRQ Overhead는 모델링하지 않았다.

## 측정 결과

| 시나리오 | 프레임 | 기존 버스 바이트 | 최적화 버스 바이트 | 실제 화면 데이터 바이트 | 전송 Page 횟수 | 버스 바이트 절감 |
|---|---:|---:|---:|---:|---:|---:|
| 고정 1D 진단 화면 | 40 | 42,320 | 360 | 320 | 4 | **99.15%** |
| 1D 진단 + 수동 각도 텍스트 변화 | 60 | 63,480 | 1,326 | 726 | 60 | **97.91%** |
| 가상 레이더 스캔선 변화 (합성 패턴) | 120 | 126,960 | 23,414 | 15,004 | 841 | **81.56%** |
| 전체 화면 0/1 반전 | 40 | 42,320 | 43,718 | 40,518 | 320 | **−3.30%** |

모든 시나리오에서 **GDDRAM 1,024B Bit-Exact 정합**. 전송 트랜잭션 총 2,450회, 명령·데이터 트랜잭션 쌍이 일치하며 시뮬레이터 Assertion PASS.

### 100kHz I2C 직렬화 시간의 참고 추산

9클록/바이트(ACK 포함)만 고려한 **이론상 직렬화 시간**, CPU 실행 시간/전력 또는 실제 보드 지연이 아니다.

| 시나리오 | 기존 | 최적화 |
|---|---:|---:|
| 고정 1D 진단 화면 (40프레임 합) | 3,808.80ms | 32.40ms |
| 각도 텍스트 변화 (60프레임 합) | 5,713.20ms | 119.34ms |
| 합성 레이더 스캔 (120프레임 합) | 11,426.40ms | 2,107.26ms |
| 전체 프레임 반전 (40프레임 합) | 3,808.80ms | 3,934.62ms |

**해석**: 정적인 텍스트/제한된 영역의 업데이트가 많은 화면에서는 전송량 이득이 상당하다. 반면 거의 모든 바이트가 바뀌는 경우에는 Page별 열 주소를 재설정하는 명령이 추가되어 3.30% 정도 버스 바이트가 늘어났다. 따라서 화면 변화 패턴에 따라 Dirty Update를 Full-Frame으로 전환하는 정책은 후속 최적화 후보이나, 실제 I2C 타이밍과 비용을 측정하기 전에 임의 정책을 적용하지 않는다.

## 통과 범위/미검증

- 통과: 최적화 OLED 실제 C 소스 전송량, 주소 명령 해석, 1,024B GDDRAM 정합, 호스트 회귀(버퍼 불변성·오류 복구·eDMA 레지스터 설정 Mock 포함).
- 미검증: S32DS ARM Build, 실물 I2C 신호 타이밍·SSD1306 호환성, 실제 eDMA CH0 구동, GPIO 버튼 반응 시간/IRQ 지연, 전력 절감률.
- 이 시뮬레이션은 `App_Update`와 실제 `RadarRenderer_Draw`를 직접 구동하지 않는다. 고정 진단 텍스트는 실제 애플리케이션이 사용하는 문자열을 재현하며, 스캔은 **합성 기하 패턴**이다.
