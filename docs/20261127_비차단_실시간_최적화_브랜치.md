# MP_TerP — 비차단 실시간 최적화 브랜치 (2026-11-27)

- 브랜치: `opt/nonblocking-edma-20261127`
- 원본 기준: `final/radar-system-20261126` / `6dbc4909d40e0602bdab64bc7c4cfb6ddf546736`
- 목적: 기존 검증된 입출력 핀과 구동 기능을 유지하면서 Main foreground의 Worst-Case Execution Time을 줄이고, CPU의 OLED 대기 시간을 없애는 것
- **현재 단계:** 1차 비차단 LPI2C + OLED Dirty Page + 1ms 협력형 App FSM + Relay LPIT one-shot. **실제 eDMA(TCD/DMAMUX)는 아직 미구현**
- 안전: 실제 릴레이 코일은 GPIO에 직접 연결하지 말 것. PTC4(SWD_CLK)/PTC5(JTAG)는 건드리지 않으며 외부 버튼 PTC8/PTC9 유지

## 변경 사항

| 기능 | 최종 기준 브랜치 | 최적화 브랜치 |
|---|---|---|
| OLED 반복 갱신 | 1KB 전체, LPI2C TDF/SDF Busy-wait | SSD1306 GDDRAM 8 Page × 128B 비교, 변경 Page만 전송 |
| OLED 전송 | `OLED_Update` 동기 호출 | `OLED_RequestUpdate` 예약 후 `OLED_Service`에서 1회에 MTDR 1개 이하 공급 |
| LPI2C 버퍼 | 렌더링 버퍼 직접 참조 | Page별 128B 불변 스냅샷, STOP 완료 후 표시 상태 확정 |
| 오류 복구 | 동기 함수 타임아웃 반환 | 200ms per-transaction watchdog, 버스 재초기화 후 250ms 재시도 |

| 계측 | OLED/루프 전용 변수 없음 | OLED Page/Bytes/Errors, DWT BoardSystem_Update() 최근/최대 사이클 |
| eDMA | 없음 | **아직 없음.** 별도 하드웨어 검증 단계 |

### OLED 전송 API

- `OLED_Init()`은 초기 부팅에서 기존의 *동기식* OLED 초기화 및 전체 Clear 전송을 유지한다.
- Stage5의 App `oled_flush`는 `OLED_Update()`가 아니라 `OLED_RequestUpdate()`를 호출한다.
- `BoardSystem_Update`는 매 반복마다 `OLED_Service(TimerManager_GetTickMs())`를 호출한다.
- `OLED_Service`는 SSD1306의 `0x21`(Column address) 및 `0x22`(Page address) 설정 후 해당 Page만 보낸다.
- 전송 중 프레임버퍼는 계속 변경 가능하나, Tx Page 스냅샷 `s_page_data`는 완료 전까지 변경되지 않는다.
- 화면이 변화 없으면 I2C 데이터 전송을 생략한다.
- `OLED_PortAsyncService`는 TDF를 *한 번 읽고*, 공급 가능할 때만 MTDR *최대 한 워드*를 쓴다. `for` busy-wait는 없다.

**주의:** 메인 루프는 현재도 계속 반복된다. 인터럽트나 eDMA 전송 완료를 기다리는 `WFI` 저전력 방식은 아직 아니다. 따라서 CPU 점유 시간 감소와 저전력화를 동일시하지 말 것.

### LPIT 자원

| 채널 | 담당 |
|---|---|
| CH0 | 28BYJ Stepper 스텝 |
| CH1 | Ultrasonic Trigger 10µs |
| CH2 | 1ms system tick |
| CH3 | 200ms Active-High Relay one-shot 종료 |

Relay 타이머는 시작 *직후* HIGH로 출력되므로 설정한 200ms보다 몇 CPU cycle 짧을 가능성이 있다. 실측 검증이 필요하며 foreground fallback도 유지한다.

### S32DS Expressions 확인

- `g_stage_state == 2`, `g_stage_error == 0` (부팅/정상 실행)
- `g_stage_oled_pages_sent`: 실제 전송을 완료한 128B Page 횟수
- `g_stage_oled_pages_skipped`: 이전 전송 이미지와 동일하여 생략한 Page 횟수
- `g_stage_oled_data_bytes`: 화면 데이터 전송량 (`128 * pages_sent`)
- `g_stage_oled_errors`: LPI2C 오류/전송 timeout 누적
- `g_stage_oled_busy`: 현재 화면 변경분 전송 예약/진행
- `g_stage_update_cycles_last`, `g_stage_update_cycles_max`: DWT 기준 한 번의 `BoardSystem_Update` 경과 Cycle. CPU clock 80MHz이면 `cycles / 80` ≈ µs. ISR 선점 시간도 포함.
- `g_stage_relay_pulses`: 유효한 소프트웨어 조준 완료 이후 Relay pulse 횟수

### 기존 Stage5 모드 주의

기본 모드는 센서가 Servo에 기계적으로 결합되지 않았다고 가정하는 1D 진단이다. 외부 가변저항으로 `30~150°` 수동 조준각을 고르고 AIM 버튼으로 Stepper를 회전한다. 실제 표적 각도를 추적하는 기능은 `MP_TERP_CONFIRM_COUPLED_GEOMETRY`를 명시적으로 켜고 물리 결합을 확인해야 한다.

### 보드 확인 절차

1. **기존 최종 브랜치가 정상 작동함을 확인한 경우에만** 이 브랜치를 별도로 Clean/Build.
2. 모터/릴레이 부하를 분리한 상태로 S32DS Flash & Debug 및 DWT/OLED 진단 변수 확인.
3. Servo, Ultrasonic, Stepper, 두 외부 버튼, ADC를 순차적으로 연결해 구동/IRQ 검증.
4. OLED가 150ms 주기와 맞게 갱신되며, 변화가 없을 때 `pages_sent`가 증가하지 않는지 확인.
5. LCD 정상 갱신과 Relay pulse 실제 길이를 Logic Analyzer/오실로스코프로 측정.
6. CPU 전송과 향후 eDMA 전송의 **전체 I2C bus time, foreground latency, 최대 업데이트 cycles, button latency, jitter**를 비교할 것.

### 현재 검증 범위

- GitHub Actions의 gcc 호스트 테스트에서 OLED Dirty Page, 변경 없음 skip, 전송 중 렌더링 안전성, 오류 후 재시도 시험 추가
- ARM MCU 컴파일, 실제 LPI2C 하드웨어 동작, ISR 우선순위, eDMA 및 지터 측정은 **별도 보드 실험 전까지 미검증**
- 변경된 SSD1306 Page Address 설정이 사용 중인 OLED 모듈에서 동작하는지 실기 검증 필요

## 후속 변경 대상 (이번 단계에 구현되지 않음)

1. `LPI2C0` DMA 요청과 S32K144 `DMAMUX`/eDMA TCD 연결을 하드웨어에서 확인
2. RAM Page → LPI2C MTDR의 **16bit command/data word** 전송과 FIFO/STOP 완료 동기화를 eDMA로 전환
3. DMA 활성 상태의 버퍼 소유권·오류 복구·전력/CPU 지표 계측
4. 측정 결과에 따라 레이더 처리의 계산만 제한된 작업 단위로 분할 (무조건 루프 분할 금지)
5. 필요 시 idle/WFI 도입; DMA 또는 IRQ 기반 OLED 전송이 확립된 뒤 시도

NXP S32K1xx Cookbook(AN5413), S32K1xx RM의 eDMA, DMAMUX, LPI2C 장을 참조하여 보드 설정 확인.
